1What I Understand This Project To Be

RoomMates is not a roommate-finding or social app. It is a small, correctness-critical financial ledger wrapped in a friendly SaaS-style interface. Everything else — the dashboard, the charts, the notifications — is presentation on top of one core question:

The one question the app answers

"Given everything this group has spent, who owes whom, and how few payments can settle it?"

The product model in one paragraph: a user registers, creates a room (a shared-expense group) and gets a unique room code such as RM-7X92AB. They share the code; others join with it. Anyone in the room logs expenses — who paid, how much, for what, and which members it should be split between. The system continuously maintains each member's net balance, shows how each person compares to the group, and proposes a minimal set of payments to settle up. Every expense is permanent: edits are recorded as revisions rather than overwrites, and deletions are soft. One user can belong to many rooms (Home, Office, Trip, Veg group, Non-veg group), and room data never mixes.

What makes this harder than it looks

A naive version of this app is a weekend build. The requirements you have written are not the naive version — three of them are genuinely hard, and they are the ones that decide whether the architecture holds up:

RequirementWhy it is hard
Historical accuracy when membership changes
Spec §3, §29		 If shares are computed at read time from current membership, then the moment a 5th person joins, every past expense silently re-splits 5 ways and last month's report changes. Old settled balances become wrong.
Edits must never destroy the previous value
Spec §8, §9		 Calculations must use the latest value while the audit trail keeps every prior one — so the expense document and its history cannot be the same record.
Flexible splits (equal / custom / percentage / subset)
Spec §6, §7		 Once a dinner can be split between 3 of 5 people, "total ÷ members" stops being anyone's fair share. The whole calculation model has to change shape. See §2.2 — this is the one correction I'd make to the spec.

Sections 2 and 3 of this document are my proposed answers to those three. The rest is the build plan.

2The Three Core Design Decisions

2.1  Snapshot the split at write time — never recompute it at read time

This single decision solves the historical-accuracy requirement (§3, §29) completely, and it costs almost nothing.

When an expense is created, the server resolves the split immediately and stores the result as an immutable list of per-member shares on the expense document itself:

// One expense document, after the server resolves the split
{
  amount: 2000, paidBy: [{ user: "rohit", amount: 2000 }],
  splitType: "equal",
  shares: [                      // ← frozen at creation. Never recomputed.
    { user: "alok",  amount: 500 },
    { user: "rahul", amount: 500 },
    { user: "aman",  amount: 500 },
    { user: "rohit", amount: 500 }
  ]
}

Now a member joining or leaving is just a change to the room's member list. It cannot touch a single past expense, because no past expense refers to "current members" — each one carries its own participant list. Historical reports are stable by construction, not by careful coding.

Consequence

Every figure in the app — balances, totals, per-member spend, settlements, any date-ranged report — becomes a simple sum over these frozen share rows. There is no "recalculate history" code path to get wrong, because there is no recalculation.

We still store joinedAt / leftAt on each membership as the spec asks, but they serve reporting and display ("who was here in July?"), not the money math. Members who leave are marked inactive, never removed, so their name still renders on old expenses.

2.2  Balance = paid − owed. "Average" is a display metric, not the fair share.

One correction to the spec

§5 and §11 define fairness as difference from the average (total ÷ members). That is correct only when every expense is split equally among all members. But §6 and §7 explicitly require custom splits, percentage splits, and subset splits — the veg/non-veg dinner case. The moment one dinner is split between 3 of 5 people, the average is no longer what anyone actually owes, and a dashboard built on it will show numbers that don't reconcile with the settlement page.

The model that stays correct in every case:

paidi     = Σ amounts member i actually paid out
owedi     = Σ member i's share rows across all active expenses
settledi  = Σ confirmed settlements i paid − Σ i received

balancei  =  paidi − owedi + settledi

balance > 0  →  member is owed money (creditor)
balance < 0  →  member owes money    (debtor)
Σ balance    =  0   ← invariant, assert this in tests

Note the third term: settlements adjust balances without touching expense records, exactly as §12 requires. Keep the average — it is a genuinely useful "am I spending more than the group?" signal, and your §11 comparison table is a good screen. Just label it as a comparison metric and drive "you owe / you are owed" from balance. When all splits happen to be equal, the two agree anyway.

2.3  Expenses are append-only: revisions, not overwrites

Three rules give you the full audit trail in §8 and §9 with very little machinery:

  • Edit → write the old field values into an ExpenseRevision document, then update the expense and set isEdited: true. The expense holds the current truth; revisions hold the past.
  • Delete → set isDeleted: true and deletedAt. Every query filters on isDeleted: false. Nothing is ever removed from the database.
  • Settle → insert a Settlement document. Expenses are never modified by a settlement.

Because an edit changes the amount, it also changes the shares — so the edit path re-resolves the split and writes a new frozen shares array, with the previous one preserved in the revision. Authorization is strictly enforced server-side: only expense.createdBy may edit; creator or room admin may delete.

3The Calculation Engine

Per §28, this lives in server/src/services/calculation/ as pure functions that take plain data and return plain data — no database access, no Express, no React. That is what makes it unit-testable, and financial logic must be tested.

3.1  Settlement: greedy minimum cash flow

Given the balances, we want the fewest payments that zero everyone out. The standard approach:

  1. Split members into creditors (balance > 0) and debtors (balance < 0).
  2. Sort both by magnitude, largest first.
  3. Match the largest debtor against the largest creditor. Transfer min(|debt|, credit).
  4. Whichever side hits zero drops out; repeat until all balances are zero.

This yields at most n−1 transactions for n members, and in practice far fewer. Using your own worked example from §5:

MemberPaidOwed (equal split)BalanceRole
Alok₹400₹500−₹100debtor
Rahul₹200₹500−₹300debtor
Aman₹600₹500+₹100creditor
Rohit₹800₹500+₹300creditor

The algorithm pairs Rahul (−300) with Rohit (+300), then Alok (−100) with Aman (+100):

Result — 2 transactions

Rahul → Rohit ₹300  •  Alok → Aman ₹100

Your spec §5 sketches a 3-transaction settlement (Rahul→Aman ₹200, Rahul→Rohit ₹100, Alok→Rohit ₹200). Both are valid — every balance reaches zero — but the greedy version needs one payment fewer, which is what §5's own "minimize unnecessary transactions" asks for. Worth knowing the spec's illustration and the implementation will differ here.

3.2  Money is stored in paise, never in rupees

Non-negotiable

Store all amounts as integer paise (₹500.50 → 50050). JavaScript floats cannot represent 0.1 exactly; a percentage split of ₹1000 three ways in floating point leaves stray fractions that accumulate until balances no longer sum to zero and the settlement page shows ₹0.01 phantom debts. Convert to rupees only at the display layer.

Related: an equal split of ₹1000 among 3 gives 33333 / 33333 / 33333 paise = 99999, one paise short. The engine assigns remainder paise deterministically (first n participants get +1) so shares always sum exactly to the expense total. This is a required unit test.

3.3  Split resolution

Split typeRuleValidation (server-side)
EqualTotal ÷ number of selected participants, remainder distributed deterministicallyAt least 1 participant
CustomExplicit amount per participantΣ shares must equal expense total exactly
PercentageTotal × pct, remainder distributed deterministicallyΣ percentages = 100; Σ resulting shares = total
SubsetAny of the above, over a chosen subset of membersEvery participant is an active room member

The veg/non-veg scenario in §7 is just subset split with tags — no special-casing. A room has free-form member tags ("veg", "non-veg", "1st floor"); selecting a tag pre-selects those members in the Add Expense form. Users who want fully separate books can still create a second room, since the spec allows both.

4System Architecture

React client — Vite + Tailwind
Pages · reusable components · React Router with protected routes · Context for auth + active room · lazy-loaded routes · Recharts for the three dashboard charts. No business logic here.
↕   REST over HTTPS, JWT in Authorization header   (+ Socket.IO later)
Express API
routes → middleware (auth, room membership, role) → validators (Zod) → controllers. Controllers stay thin: parse, delegate, respond.
↓
Service layer — including the calculation engine
All business rules live here. The calculation engine is a set of pure functions with no DB or HTTP dependency, so it can be tested directly. This is the heart of the app.
↓
Mongoose models → MongoDB Atlas
Users · Rooms (with embedded members) · Expenses (with frozen shares) · ExpenseRevisions · Settlements · Notifications. Compound indexes on every hot query path.
The rule that keeps this maintainable

Business logic never leaks upward. A controller that adds two numbers together is a bug in the making — if the number matters, a service computes it. This is what §41 is really asking for, and it is also what lets the entire money model be tested without spinning up a server.

6Risks & Open Decisions

6.1  Where this project is most likely to go wrong

RiskMitigation
Floating-point moneyInteger paise everywhere, enforced at the model layer. The single highest-value rule in this document.
Recomputing historyFrozen shares[] (§2.1). If you take one architectural idea from this plan, take this one.
Average vs. balance driftDrive all money statements from balance; treat the average as a comparison metric only (§2.2).
Client-side-only authorizationHiding an Edit button is not security. Phase 12 exists specifically to attack this.
Scope creep§39 is right — this is a ledger, not a social network. Phases 1–8 are the product; 9–13 make it shippable. Anything else is v2.
Building the UI before the enginePhases are ordered deliberately: data model and money math before dashboards. §40 says the same thing.

6.2  Decisions worth making before phase 1

QuestionMy recommendation
JavaScript or TypeScript?TypeScript, if you are comfortable with it. In an app whose core is money arithmetic, having the compiler check that a share array actually carries {user, amount} pays for itself. If it would slow you down, plain JS with Zod validation at the boundaries is a fine second choice.
Refresh tokens?Skip for v1. A single access token with a sane expiry and a clean 401 → login redirect meets §14. Add refresh later if session length becomes a real complaint.
Socket.IO in v1?Optional, per §30. Emit notification events from the service layer from day one; wiring sockets in afterwards then costs about a day.
Receipt image uploads?Cloudinary free tier. Never store binaries in MongoDB.
Multi-currency?Not in v1. Fix on ₹ (INR). Retro-fitting currency into a ledger is painful, so if you think you will ever need it, add a currency field to Room now and leave it constant.

6.3  Suggested order of work

Phases 1 → 8 are strictly sequential; each genuinely depends on the one before. From phase 9 onward the order is flexible — if you have a demo or submission deadline, do phase 13 (seed data + README + deploy) early so there is always something running that you can show, then continue polishing.

The shortest path to something demonstrable

Phases 1 → 5 plus a rough dashboard gives you the complete §43 acceptance workflow in about 2.5 weeks part-time: register, create a room, join by code, add expenses, see balances and settlements. Everything after that raises quality rather than adding capability — which is the right shape for a project you may need to show before it is finished.
